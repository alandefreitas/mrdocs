= Plugins
:url-plugins: https://github.com/cppalliance/mrdocs/tree/{page-origin-refname}/examples/plugins

A plugin is a shared library that Mr.Docs loads as it starts up, handing it a context. Through that context, the plugin installs what it provides, so the rest of the run sees it as if it had shipped with the tool: generators, which turn the corpus into output, and transforms, which change the corpus before any generator sees it.

Reach for a plugin when you need {cpp}: a format whose rules are awkward to express in templates, work heavy enough to justify compiled code, or a generator that links to a C or C++ library on its own (e.g. SQLite to write the corpus into a database another tool queries, or a PDF library to typeset the reference). The lighter options remain xref:extensions/data-driven-generators.adoc[data-driven generators] (templates only) and xref:extensions/script-generators.adoc[script generators] (Lua or JavaScript). The difference from xref:extensions/as-library.adoc[Mr.Docs as a library] is that a plugin runs inside the ordinary `mrdocs` tool: you keep the command line, the configuration, and everything else Mr.Docs does, and you do not build Mr.Docs or LLVM.

The {url-plugins}/stats[`stats`^] example is the whole of what follows, as a directory you can copy: the plugin, and a small project documented with it.

== Building a plugin

A plugin is a CMake module library that links the `mrdocs` tool:

[source,cmake]
----
find_package(mrdocs REQUIRED CONFIG)
add_library(stats MODULE plugin.cpp)
target_link_libraries(stats PRIVATE mrdocs::mrdocs)
set_target_properties(stats PROPERTIES
    CXX_VISIBILITY_PRESET hidden
    VISIBILITY_INLINES_HIDDEN ON)
----

Linking the tool resolves the Mr.Docs symbols the plugin calls, and the Mr.Docs headers are the only other thing the plugin builds against: the public headers declare the LLVM types they name without defining them, and the tool carries LLVM and Clang inside it.

In the default build (static and not sanitized, which is what the release packages are), the `mrdocs` executable exports the Mr.Docs API, meaning the functions and variables in the `mrdocs` namespace together with the type information and vtables of its classes, and nothing of LLVM, Clang, Lua or JerryScript. A plugin that bundles its own copy of one of those libraries therefore binds to its own copy and never to the one inside the executable. A plugin that needs LLVM or Clang, or that reaches into Mr.Docs's internal headers, is not supported against the release tool: it has to be built against, and loaded by, a Mr.Docs built from source. Two kinds of build keep the full export table instead: a shared build (`MRDOCS_BUILD_SHARED`), where the API lives in the library, and a sanitized build, where plugins bind to the sanitizer runtime through the executable. `MRDOCS_NARROW_EXPORTS` is a CMake cache setting (`AUTO`, `ON` or `OFF`) whose default `AUTO` turns narrowing off in shared and sanitized builds. The narrowed table is also why the fallback backtrace of a crash shows addresses instead of function names for LLVM and Clang frames: configure with `MRDOCS_NARROW_EXPORTS=OFF` to get names back, or symbolize the addresses with `llvm-symbolizer` or `addr2line`.

A plugin should compile with hidden visibility, as the example above does, so that its own symbols stay its own. Without it, a call from a plugin to one of its own functions can bind to a function of the same name in the tool. The entry points stay visible, since cpp:MRDOCS_PLUGIN_MAIN[] marks them with cpp:MRDOCS_PLUGIN_EXPORT[].

The resulting library has to be built the way the Mr.Docs that will load it was built. That requirement is checked rather than assumed, and the section on xref:#_keeping_a_plugin_loadable[keeping a plugin loadable] is about what it covers.

== The entry point

The cpp:MRDOCS_PLUGIN_MAIN[] macro defines the function Mr.Docs calls, naming the cpp:PluginContext[] parameter it receives. This plugin installs one of each thing a plugin can install:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/stats/plugin.cpp[tag=main]
----

The context is how a plugin reaches Mr.Docs: cpp:PluginContext::installGenerator[] adds a generator, cpp:PluginContext::installTransform[] adds a transform, and cpp:PluginContext::config[] returns the configuration the run was started with, already loaded and normalized, in case what the plugin installs depends on it. The reference is valid for the duration of the call.

Along with the entry point, the macro defines two functions that report how the library was built, and Mr.Docs calls both before it calls the plugin. One reports cpp:MRDOCS_PLUGIN_BUILD_ID[], the Mr.Docs build the plugin was compiled against; the other reports cpp:MRDOCS_PLUGIN_STDLIB_TAG[], the standard library. The macro writes all three from the headers the plugin is compiled against, so they always agree with each other.

== Transforming the corpus

A plugin can also install a cpp:Transform[]: a pass that runs once, after the corpus is built and finalized and before any generator runs, so what it changes is what every output format sees. Where a generator is handed the corpus as `const`, a transform is handed it mutable, and may read it, change the symbols it finds, or both. Everything a symbol holds is in reach, including the lists of members that the generators walk to decide what to write, and the generators rely on what finalization left there:

include::partial$transform-invariants.adoc[]

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/stats/plugin.cpp[tag=transform]
----

The example's transform gives a symbol with no brief a placeholder one, so that the gap shows up in the output instead of a blank space. The placeholder is the `text` option of the transform's own `transform-options` block, or `Undocumented.` when there is none:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/stats/plugin.cpp[tag=apply]
----

The sample project leaves one function undocumented, and the global namespace has no doc comment either, so the transform gives both a brief, and the generator counts every symbol among those that have one.

A plugin's transforms and the ones an extension script registers with `mrdocs.register_transform` run as one pipeline, in the order they were registered. Plugins load before scripts, so the transforms a plugin installs run first, in the order it installed them, and the scripts' follow in the order their files load. Each transform receives its own `transform-options.<id>` block as the `params` argument of cpp:Transform::apply[], where `<id>` is what cpp:Transform::id[] returns, or an empty object when the configuration has none. With this configuration, `brief-filler` gets `{ "text": "TODO" }` and a script transform registered as `brief-checker` gets `{ "suffix": "checked" }`:

[source,yaml]
----
transform-options:
  brief-filler:
    text: TODO
  brief-checker:
    suffix: checked
----

After a transform runs, the corpus forgets the lookups by name it remembered, so a transform that renames a symbol is seen by the next one, and by the generators, under the new name. An error from a transform stops the run before any generator sees the corpus, and the diagnostic names the transform through cpp:Transform::id[]: ``the transform "brief-filler" failed: ...``.

== Installing a plugin

Mr.Docs looks in the `plugins` subdirectory of every addon root, that is, under both the xref:configuration/reference.adoc#addons_option[`addons`] directory and each xref:configuration/reference.adoc#addons-supplemental_option[`addons-supplemental`] directory, in that order:

[source]
----
my-addons/
└── plugins/
    ├── stats.dll        <1>
    └── stats/           <2>
        └── sqlite3.dll
----
<1> `.dll` on Windows, `.so` on Linux, `.dylib` or `.so` on macOS.
<2> The shared libraries the plugin depends on, if it has any.

Every library in such a directory is loaded, in name order within a root, and roots are visited in the order the configuration lists them. One library reachable through several roots is loaded once. Anything that is not a library is ignored, and so are subdirectories, so a directory can hold a README, an import library, debug information, or the libraries a plugin depends on without confusing the search.

Each `plugins` directory adds its libraries to the run, whereas a template in a supplemental root replaces the default one at the same path. The same plugin copied into two roots is therefore loaded twice, and the second copy fails on the generator id the first one installed.

A plugin that depends on shared libraries of its own keeps them in a subdirectory named after it: `plugins/stats` for `stats.dll`. On Windows, Mr.Docs adds that subdirectory to the search for the plugin's dependencies while it loads the plugin, so the search covers the plugin's directory, that subdirectory, the directory of the `mrdocs` executable and the system directories, and not the current directory or `PATH`. On Linux and macOS, the plugin finds them through its run path, `$ORIGIN/stats` or `@loader_path/stats`, which CMake records with:

[source,cmake]
----
set_target_properties(stats PROPERTIES
    INSTALL_RPATH "$ORIGIN/stats"   # "@loader_path/stats" on macOS
    BUILD_WITH_INSTALL_RPATH ON)
----

A library that cannot be loaded, does not export the entry points, was built for another Mr.Docs build or with another standard library, or reports an error of its own stops the run, and the diagnostic names the library.

A library is opened with all of its symbols resolved at once, and keeps them to itself: a plugin that refers to something Mr.Docs or the system does not provide is refused while loading instead of crashing the first time it calls it, and two plugins cannot replace each other's functions. On Linux and macOS the message names the missing symbol; on Windows it only says that a module or procedure could not be found. A plugin built against another build of Mr.Docs, or with another standard library, often refers to symbols this Mr.Docs does not have, and is refused the same way, so check that the plugin was built against the Mr.Docs that loads it. A dependency that is not in the plugin's subdirectory is found, on Linux and macOS, the usual way for the plugin: through its RPATH or RUNPATH, through `LD_LIBRARY_PATH` (`DYLD_LIBRARY_PATH` on macOS), or in the system directories; the directory of the `mrdocs` executable is not searched. A loaded plugin stays loaded until the process ends, and its entry point runs once per process: a tool or program that loads plugins again, for another run, reuses what the plugin installed the first time. What depends on the run, such as a setting, belongs in a transform's `apply`, which receives the configuration and the params of every run, rather than in the entry point.

Once the library is there, the generator it installs is selectable like any other, through the xref:configuration/reference.adoc#generator_option[`generator`] option:

[source,yaml]
----
generator: stats
----

For the sample project that comes with the example, whose input describes a handful of symbols, the generator writes:

.`stats.txt`
[source,text]
----
include::example$examples/plugins/stats/sample-project/stats.txt[]
----

== Keeping a plugin loadable

A plugin and Mr.Docs pass {cpp} objects between them: the plugin allocates a generator that Mr.Docs destroys, and both inline the standard library types the API exposes. Two things have to hold for that, and Mr.Docs checks both before it calls a plugin, so a mismatch is a diagnostic naming the library rather than a crash somewhere unrelated.

The first is the build. A plugin sees Mr.Docs types by their layout, and that layout changes in most commits, so a plugin loads only into the exact Mr.Docs build it was compiled against. cpp:MRDOCS_PLUGIN_BUILD_ID[] is the identity of that build, the same text as `mrdocs::project_release_with_build`, such as `2026.10.26+662773e585c8`. A plugin compiled against the headers of one build and loaded into another is refused:

[source,text]
----
the plugin "plugins/stats.so" was built for MrDocs 2026.10.26+662773e585c8, and this is 2026.11.2; rebuild it against this MrDocs
----

The second is the standard library, and not the compiler. The two sides have to use the same standard library, configured so that it lays its types out the same way, so the plugin reports the library and the settings that move those layouts: the dual ABI and debug mode of libstdc++, the ABI version of libc++, and the C runtime (dynamic or static, release or debug) and iterator debug level of the MSVC STL. Mr.Docs refuses a plugin whose report differs from its own. The release of the library and the compiler are not part of the report. GCC and Clang share libstdc++ on Linux, so a plugin built with Clang loads into a Mr.Docs built with GCC. A plugin built with `-stdlib=libc++` is refused by a Mr.Docs that uses libstdc++, usually at load time: the standard library's namespace is part of every symbol name, so the plugin refers to `std::__1` symbols that Mr.Docs does not have, and the message names one of them. The same holds for a plugin built with `-D_GLIBCXX_DEBUG`, whose containers live in the `std::__debug` namespace: one that passes containers to Mr.Docs functions is refused at load with an undefined symbol. Only a plugin that does not reach such a function gets as far as the library's report, which then differs:

[source,text]
----
the plugin "plugins/stats.so" was built with libstdc++, cxx11-abi 1, debug on, and this MrDocs with libstdc++, cxx11-abi 1, debug off; rebuild it with the same standard library and settings
----

On Windows, Mr.Docs and its plugins use the DLL runtime (`/MD`), which is what CMake selects by default. Each side frees memory the other allocated, and that works only when the two share the runtime's heap. A plugin built with the static runtime (`/MT`) is refused, since its report says `crt static` where Mr.Docs's says `crt dynamic`.

Plugins need a Mr.Docs that can load them, which is every build except two kinds. A statically linked Mr.Docs has no dependable way to load a shared library while it runs, and cannot produce one either, since the startup files a static link brings in carry relocations a shared object cannot hold. CMake detects `-static`, `--static`, `-static-pie` and `-Wl,-static` in `CMAKE_C_FLAGS`, `CMAKE_CXX_FLAGS` and `CMAKE_EXE_LINKER_FLAGS`, and their per-configuration variants (the four standard configurations, the build type and every entry of `CMAKE_CONFIGURATION_TYPES`); pass `-DMRDOCS_PLUGIN_MODULES_SUPPORTED=OFF` when the flag comes from somewhere else, such as a toolchain file or `LDFLAGS`. A shared build keeps the API in the mrdocs-core library rather than in the tool a plugin links. A Mr.Docs that cannot load plugins reports a plugin it finds rather than loading it, and the package config reports the answer as `MRDOCS_BUILT_PLUGIN_MODULES`, so a build can ask before it tries. The separate `MRDOCS_BUILD_PLUGIN_MODULES` option only decides whether a Mr.Docs build runs its own plugin tests and examples; it defaults to the same answer, and turning it on where plugins are not supported is a configuration error.

The published Windows and macOS binaries load plugins. The Linux binary is linked statically, so that one binary runs across distributions, and is built without plugin support. A Mr.Docs you build yourself on Linux links dynamically by default, and loads plugins.

== Building against more of Mr.Docs

Two cases bring in dependencies beyond the Mr.Docs headers. A plugin that reaches past the public headers into Mr.Docs's internal ones, as one supplying its own compilation database would, builds against LLVM as well, and is not supported against the release tool, which exports none of LLVM. And a Mr.Docs built to re-export its private dependencies, which the package config reports as `MRDOCS_BUILT_REEXPORT_DEPENDENCIES`, sends `find_package` looking for them (LLVM, Clang, JerryScript and Lua) whether or not the plugin ever names them. A Mr.Docs built the default way bundles them, so `find_package` needs the installation alone.
