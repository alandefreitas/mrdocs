= Plugins
:url-plugins: https://github.com/cppalliance/mrdocs/tree/{page-origin-refname}/examples/plugins
:url-header: https://github.com/cppalliance/mrdocs/blob/{page-origin-refname}/include/mrdocs/plugin.h
:url-wrapper: https://github.com/cppalliance/mrdocs/blob/{page-origin-refname}/include/mrdocs/plugin.hpp

A plugin is a shared library that Mr.Docs loads as it starts up, handing it an environment. Through that environment, the plugin registers what it provides, so the rest of the run sees it as if it had shipped with the tool: generators, which turn the corpus into output, and transforms, which change the corpus before any generator sees it.

Reach for a plugin when you need compiled code: a format whose rules are awkward to express in templates, work heavy enough to justify native speed, or a generator that links to a C or C++ library on its own (e.g. SQLite to write the corpus into a database another tool queries, or a PDF library to typeset the reference). The lighter options remain xref:extensions/data-driven-generators.adoc[data-driven generators] (templates only) and xref:extensions/script-generators.adoc[script generators] (Lua or JavaScript). The difference from xref:extensions/as-library.adoc[Mr.Docs as a library] is that a plugin runs inside the ordinary `mrdocs` tool: you keep the command line, the configuration, and everything else Mr.Docs does, and you do not build Mr.Docs or LLVM.

A plugin talks to Mr.Docs through a C interface, declared in the single header {url-header}[`mrdocs/plugin.h`^]. No {cpp} type crosses it. The corpus, the configuration and the parameters reach the plugin as the same values extension scripts see as `ctx.corpus`, `ctx.config` and `ctx.params`, so a plugin reads and writes symbols the way a Lua or JavaScript extension does, and the fields of xref:generators/reference.adoc[the DOM reference] are the fields it finds. It follows the loading model of Clang's plugins (a shared library loaded into the tool, which adds to the tool's registries) and the ABI model of https://nodejs.org/api/n-api.html[Node-API^] (opaque handles, status codes, and a version number that only grows); the xref:#why-c[section on the C interface] says why. Any C or C++ compiler can build a plugin, and a plugin can be written in C. {cpp} authors have a header-only wrapper on top of that interface, {url-wrapper}[`mrdocs/plugin.hpp`^], which this page uses for its examples: it turns failed calls into exceptions, gives values the shape of a script's values, and provides base classes for generators and transforms.

The {url-plugins}/stats[`stats`^] example is the walkthrough of this page, as a directory you can copy: the plugin, and a small project documented with it. The {url-plugins}/deprecations[`deprecations`^] example, xref:#deprecations-example[further down], is a larger plugin that reads more of the corpus.

== Building a plugin

A plugin is a CMake module library that links `mrdocs::plugin`:

[source,cmake]
----
find_package(mrdocs REQUIRED CONFIG)
add_library(stats MODULE plugin.cpp)
target_link_libraries(stats PRIVATE mrdocs::plugin)
target_compile_features(stats PRIVATE cxx_std_17)
----

`mrdocs::plugin` is an interface target that the package exports. It adds the include directory of the Mr.Docs headers and resolves the Mr.Docs functions the plugin calls: on Windows it links the import library of the `mrdocs` executable, and on macOS it tells the linker to leave undefined symbols to be resolved when the tool loads the plugin, as a Linux linker already does for a module. That covers every undefined symbol of the plugin, not just the `mrdocs_*` functions, so a misspelled function name or a library the plugin forgot to link shows up when the plugin is loaded and not when it is linked. It states no {cpp} standard and no compiler option, so a plugin written in C links it too. It is the whole build dependency: no LLVM, no Clang, no separate library to ship alongside. The plugin includes `mrdocs/plugin.hpp`, or `mrdocs/plugin.h` if it is written in C, and nothing else from Mr.Docs.

In the default build (static, not sanitized, which is what the release packages are), the `mrdocs` executable exports the functions of that header, the ones named `mrdocs_*`, and nothing else. None of the {cpp} of Mr.Docs, and none of LLVM, Clang or the other libraries it is built from, can be reached from a plugin, so there is no other symbol to bind to, and a plugin cannot pick up a copy of a library from Mr.Docs by accident. The exported names are the ABI. Two kinds of build keep the full export table instead: a shared build (`MRDOCS_BUILD_SHARED`), which defines the C API in the library, and a sanitized build, where plugins bind to the sanitizer runtime through the executable. The `MRDOCS_NARROW_EXPORTS` CMake option switches the narrowing, and is on by default only for the default build. The narrowed table is also why the fallback backtrace of a crash on Linux and macOS shows addresses instead of function names for Mr.Docs, LLVM and Clang frames: rebuild with `MRDOCS_NARROW_EXPORTS=OFF` to get the names back, or symbolize the printed addresses with `llvm-symbolizer` or `addr2line`. On Linux and macOS, the plugin tests (`MRDOCS_BUILD_PLUGIN_MODULES` with tests on) include a check that a default build exports exactly the functions the header declares.

Importing the package carries a separate condition. A Mr.Docs built the default way bundles its private dependencies, so `find_package` needs nothing besides the installation. One built to re-export them instead, which the package config reports as `MRDOCS_BUILT_REEXPORT_DEPENDENCIES`, sends `find_package` looking for LLVM and Clang whether or not the plugin ever names them.

[#wrapper]
== The {cpp} wrapper

`mrdocs/plugin.hpp` is a single header that needs {cpp}17 and exceptions. It is compiled entirely inside the plugin, and uses the functions of `mrdocs/plugin.h` and nothing else of Mr.Docs: it names no Mr.Docs type, includes no other Mr.Docs header, and binds to no symbol of the `mrdocs` executable besides the `mrdocs_*` functions. This is the role https://github.com/nodejs/node-addon-api[node-addon-api^] plays for Node-API. Everything is in the `mrdocs::plugin` namespace:

* `Env` is the environment of a callback. It gets the corpus, the configuration and the parameters, makes values, logs, and registers generators and transforms.
* `Value` is a handle to a value. It reads like a value in a script: `kind()`, `str()`, `integer()`, `boolean()`, `value["key"]`, `value[index]`, `has`, `set`, `push`, and `size`. `Array` and `Object` are `Value`s that can be iterated, in a range-based `for` loop and, in {cpp}20, with the range algorithms and views, and `Array::each` and `Object::visit` call a function for each element.
* `Scope` and `Ref` are the scopes and references of the C interface as objects that release themselves. A `Ref` kept in a generator or a transform is deleted by its destructor, which runs when Mr.Docs drops the object.
* `Generator` and `Transform` are the base classes of what a plugin registers.
* `Error` is what a failed call throws. Its message names the function and the status, followed by the reason Mr.Docs gives for the failure when it has one, and `status()` returns the status. The wrapper's own refusals, such as a null text, a negative index or a key with a NUL character in it, have the same shape and name the wrapper function, as in `Value::set failed: invalid_arg: the text is null`.

Every call that the C interface answers with a status other than `MRDOCS_STATUS_OK` throws `Error` instead, so code that reads a symbol reads straight through. The one exception is the pair that finds a symbol, `Env::find` and `Env::lookup`: when the corpus has no such symbol, they return an empty `std::optional` and do not throw, so check it before you dereference it. No exception reaches Mr.Docs: the functions the wrapper registers with it catch what the plugin throws, and give the message to `mrdocs_set_error`, so a `std::runtime_error` you throw is the error that stops the run. The classes `Generator` and `Transform` have their virtual tables compiled into the plugin, and only function pointers and a pointer to the object cross to Mr.Docs.

The wrapper has a name for each function of the interface:

A `Value` follows the rules of the handle it wraps: it is valid until the callback returns, belongs to the thread of the callback, and is a view when it comes from the corpus, the configuration or the parameters. The next sections explain those rules, and show the wrapper at work.

[#entry-point]
== The entry point

The `MRDOCS_PLUGIN_INIT_CPP` macro defines the two functions Mr.Docs looks for in a plugin. The braces that follow it are the body of the entry point, which Mr.Docs calls once while it starts, with the environment of the call. The body registers what the plugin provides, and an exception it throws stops the run with its message. This plugin registers one of each thing a plugin can register:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/stats/plugin.cpp[tag=init]
----

A plugin in C uses `MRDOCS_PLUGIN_INIT` from `mrdocs/plugin.h` instead. Its body receives a `mrdocs_env*` and returns a `mrdocs_status`:

[source,c]
----
MRDOCS_PLUGIN_INIT(env)
{
    mrdocs_transform_desc transform = { sizeof transform, "my-transform", apply, NULL, NULL };
    return mrdocs_register_transform(env, &transform);
}
----

The other function the macro defines, `mrdocs_plugin_abi_version`, reports the version of the interface the plugin was built for, which the section on xref:#_versioning[versioning] explains.

Every function of the C interface takes the environment first and returns a `mrdocs_status`: `MRDOCS_STATUS_OK`, or a code that says what was wrong with the call (an invalid argument, a value of the wrong kind, a read-only view, and so on). A function that fails leaves its output parameters alone. The wrapper throws `Error` for every status but `MRDOCS_STATUS_OK`, except that `Env::find` and `Env::lookup` turn `MRDOCS_STATUS_KEY_NOT_FOUND` into an empty `std::optional`. The environment belongs to one callback. Mr.Docs creates it before it calls into the plugin, and destroys it when the call returns, so a plugin never keeps one. The environment, and every handle it hands out, belongs to the thread that runs the callback: a plugin uses them on that thread only, and a plugin that wants to work in parallel first copies what it needs (strings, numbers) into data of its own. Mr.Docs does not promise that the callbacks of a plugin run one at a time. The `mrdocs` tool runs one generation, but a program that embeds Mr.Docs can build several corpora at once, and then the `build` of a generator and the `apply` of a transform (which every registry that loads the plugin shares) can run on different threads, each with its own environment and all with the same `data` and the same global state of the plugin. State that a callback changes, such as a counter or an open file, is the plugin's to protect, with a lock for instance. `release` runs only once no callback is running, which `releasePlugins` requires of its caller.

== Values

Everything a plugin reads or writes is a `mrdocs_value`, an opaque handle to a value that Mr.Docs owns, which the wrapper calls a `Value`. A value is `undefined`, `null`, a boolean, an integer, a string, a safe string, an array, an object, or a function; `mrdocs_get_kind` (`Value::kind`) tells which. A safe string is a string that a template helper marked as already escaped, and `mrdocs_get_string_utf8` reads it like a string. The corpus, a configuration read from a file and the parameters read from a file hold none, and a plugin can't make one, so a plugin sees one only if a program that embeds Mr.Docs put it in the parameters. A function is a value a plugin can see but not call: the `get` and `lookup` members of the corpus are functions to a script, and a plugin uses `mrdocs_corpus_find` and `mrdocs_corpus_lookup` for them. The functions that read a scalar (`mrdocs_get_bool`, `mrdocs_get_int64`, `mrdocs_get_string_utf8`) fail with `MRDOCS_STATUS_TYPE_MISMATCH` on a value of another kind (`mrdocs_get_string_utf8` takes a string or a safe string). A string is copied into a buffer the plugin provides, and the function reports its full length, so a C plugin calls it first with no buffer to learn how much room the second call needs. `Value::str` does both calls and returns a `std::string`.

Arrays and objects are views. The handle to a symbol is a view of the live symbol: `mrdocs_object_get` reads one of its fields, and `mrdocs_object_set` writes it back, with the same validation a script's assignment gets, so giving a field a value of the wrong type fails instead of corrupting the symbol. Writing into a symbol accepts strings, numbers, booleans and containers you made with the `mrdocs_create_*` functions; Mr.Docs copies them into the symbol, so changing your container afterwards does not change the symbol. Anything you read from the corpus, the configuration or the parameters is a view that is valid for the callback only, so it cannot be stored in a container of your own (`mrdocs_object_set` and `mrdocs_array_push` fail with `MRDOCS_STATUS_INVALID_ARG`), nor written into a symbol: copy the strings and numbers out of it instead. A field a symbol doesn't have, such as the documentation of an undocumented symbol, reads as `undefined`, and `mrdocs_object_has` tells it apart from a field that is there. To make values of your own, use the `mrdocs_create_*` functions.

A handle is valid until the callback that obtained it returns. Code that loops over a whole corpus would pile up handles until then, so it opens a scope with `mrdocs_scope_open` and closes it with `mrdocs_scope_close` at the end of each iteration, which releases every handle made inside. Scopes close in the reverse order they opened: closing one twice, or an outer one before an inner one, fails with `MRDOCS_STATUS_INVALID_ARG` and releases nothing. A released handle is never valid again, even after newer handles are made: a function that is given one fails with `MRDOCS_STATUS_INVALID_ARG`. The handles a visit callback makes are released when it returns. To keep a value across callbacks, make a reference with `mrdocs_ref_create`, get a handle back with `mrdocs_ref_get`, and delete the reference with `mrdocs_ref_delete`. A reference can hold values the plugin made, but not a view of the corpus, the configuration or the parameters, which are valid for the callback only: `mrdocs_ref_create` fails with `MRDOCS_STATUS_INVALID_ARG` for one. A reference shares the value with the handles that name it, so a change made through a handle is seen through the reference. `mrdocs_ref_delete` accepts a null environment, because the `release` function of a generator or transform, where a plugin deletes the references it keeps in `data`, has none. The `mrdocs` tool calls `release` after the run, before `main` returns, so the static objects of the plugin are still alive. A transform's `release` runs at the same time as a generator's, and the order among the releases of a plugin isn't specified, so a plugin that shares state between its generators and transforms keeps a count in it and frees it in the release that brings the count to zero. A program that embeds Mr.Docs and does not call `releasePlugins` gets the calls during static destruction, when static objects of a plugin may be gone. A plugin initializes once per process, however many runs load it: its `MRDOCS_PLUGIN_INIT` runs the first time and later runs only receive its transforms, so the entry point only sees the configuration of the first run. If it fails, the run fails and the process should exit, because Mr.Docs does not undo what the plugin registered before failing. `releasePlugins` is for process shutdown: after it, loading plugins fails. Loading plugins is not thread-safe. When a call fails, Mr.Docs records the reason, and the diagnostic of a callback that returns a status without a message names it. The record describes the last call only: a call that succeeds clears it. `mrdocs_last_failure` reads the reason, with the buffer and length of `mrdocs_get_string_utf8`, and does not clear it, so a plugin that wants the reason reads it right after the failure. The wrapper does so for every call it makes, which is why the `Error` it throws says why Mr.Docs refused the call, for instance that a view is read-only.

The context of a callback comes from `mrdocs_get_corpus`, `mrdocs_get_config`, and `mrdocs_get_params`. The corpus is an object whose `symbols` field is an array of every symbol, `mrdocs_corpus_find` finds one symbol by the id in its `id` field, and `mrdocs_corpus_lookup` finds one by its qualified name, like `corpus.lookup` in a script: from the global namespace, or relative to the scope of the symbol whose id you pass as the context, so an unqualified name finds a sibling. A symbol that an earlier transform renamed is found under its new name by the transforms that run after it. The keys of the configuration are the option names in camelCase: `source-root` is `sourceRoot` and `warn-as-error` is `warnAsError`, and a key spelled with hyphens reads as undefined like any other missing key. The `generator` option has no value there. The configuration and the parameters are read-only. The parameters are the object the user wrote under `generator-options.<id>` or `transform-options.<id>` for the id the plugin registered, or an empty object.

== The generator

A plugin registers a generator with `mrdocs_register_generator`, passing a descriptor: the id the generator is selected by, a name and a file extension, the function that builds the documentation, and a pointer that function is given back. Only the id and the function are required: a null name means the id, and a null file extension means none. Mr.Docs copies the descriptor. The first field is the size of the structure, which is how later versions of the interface can add fields without breaking a plugin built earlier. A generator whose id is already taken, by a built-in or by another plugin, fails the registration.

In the wrapper, a generator is a class derived from `Generator`. The constructor of the base class takes the id, the name and the file extension, and `Env::addGenerator` fills the descriptor from them, with the object as the pointer the function is given back. Mr.Docs owns the object from then on, and deletes it when it drops the generator.

The `build` function receives the environment. The corpus it finds there is read-only, and `Env::outputDir` (`mrdocs_get_output_dir`) tells it where its files go. Mr.Docs has already created that directory, with any missing parent, like it does for the generators it ships, so the plugin only writes into it. A plugin generator always gets a directory, whatever its name, so `docs/v1.2` is one. The run fails before `build`, and the message names the generator, if the `output` option is a path that exists and is not a directory, or if the run is single-page (`multipage` is false) and the path doesn't exist yet and ends in an extension, which is how a single-page generator like the XML one reads a file name. The path is UTF-8. On Windows a path made from a `std::string` reads the bytes in the ANSI code page, so a {cpp} plugin opens files through `Env::outputPath`, which returns a `std::filesystem::path`, and a C plugin converts the path with `MultiByteToWideChar(CP_UTF8, ...)` and opens it with a wide function such as `_wfopen_s`. [#transforms]
== Transforming the corpus

A plugin can also register a transform with `mrdocs_register_transform`: a pass that runs once, after the corpus is built and finalized and before any generator runs, so what it changes is what every output format sees. Where a generator gets a read-only corpus, a transform gets a writable one, and may read it, change the symbols it finds, or both. What it cannot do is create a symbol or destroy one, since a corpus keeps its storage to itself. For the same reason the `kind`, `id`, `parent` and `inheritedFrom` fields of a symbol are read-only: writing one leaves the symbol as it was. In a plugin the call fails with `MRDOCS_STATUS_READ_ONLY`, and in an extension script the assignment raises an error. A list of symbol ids, such as the `members` of a namespace or a record, can be reordered or shortened but not extended: writing an id the list didn't hold fails with `MRDOCS_STATUS_HOST_ERROR` in a plugin and raises an error in a script, because the generators follow those lists and a symbol listed under itself would never end.

A transform is a class derived from `Transform` with an `apply` function, registered with `Env::addTransform`. The example's transform gives a symbol with no brief a placeholder one, so that the gap shows up in the output instead of a blank space. Documentation has no object until a symbol has some, so the transform creates it first:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/stats/plugin.cpp[tag=apply]
----

Plugin transforms and the transforms an extension script registers with `mrdocs.register_transform` go into a single pipeline, and it runs them in registration order. Plugins load before scripts, so the transforms a plugin registers run before any script transform, and among themselves in the order the plugins load and register them. Each transform gets its `transform-options.<id>` block as its parameters, whichever kind it is. See xref:extensions/corpus-transforms.adoc#transform-order[Transform order] for the details.

== Reporting errors

A callback written with the wrapper reports an error by throwing: whatever the exception is, its message is the error, an exception with an empty message is reported as "an exception with no message", and an exception that is not a `std::exception` is reported as "unexpected exception". An `Error` from a failed call to Mr.Docs is such an exception, so a plugin that reads a field of the wrong kind stops the run with a message such as `mrdocs_get_string_utf8 failed: type_mismatch`. `Env::setError` gives a message without throwing, and only the first message of a callback is kept.

A callback in C that can't do its job calls `mrdocs_set_error` with a message, and returns a status other than `MRDOCS_STATUS_OK`. The message becomes the error that stops the run, before any generator sees the corpus if it came from a transform, and the diagnostic names the generator or the transform. A callback that fails without a message is reported by its id and the status it returned. `mrdocs_log` writes a message to the Mr.Docs log, subject to the user's log level. A warning becomes an error when the user sets xref:configuration/reference.adoc#warn-as-error_option[`warn-as-error`], like the warnings of a script, and a message at the error level makes the run exit with a failure status once it ends. A plugin that can go on after a problem logs a warning; one that can't calls `mrdocs_set_error`.

== Installing a plugin

Mr.Docs looks in the `plugins` subdirectory of every addon root, that is, under both the xref:configuration/reference.adoc#addons_option[`addons`] directory and each xref:configuration/reference.adoc#addons-supplemental_option[`addons-supplemental`] directory, in that order:

[source]
----
my-addons/
└── plugins/
    └── stats.dll        <1>
----
<1> `.dll` on Windows, `.so` on Linux, `.dylib` or `.so` on macOS (CMake gives a module the `.so` suffix there).

The suffix decides what Mr.Docs treats as a library. It has to be lower case, because the comparison is exact (`Stats.DLL` is not opened), and it has to be the last part of the name: `stats.so` is a plugin, while `stats.so.debug` is not. On Linux a versioned name such as `libstats.so.1` is not a plugin either; on macOS the version comes before the suffix, so a versioned `libdep.1.dylib` is still a library and belongs in `plugins/lib`, not in `plugins`. A plugin is a module meant to be loaded, not a library meant to be linked against, so it carries no version in its file name.

Every library directly in such a directory is a plugin: Mr.Docs opens it, in name order within a root, and roots are visited in the order the configuration lists them, and it has to export both entry points and initialize, or the run fails with the message of the section on xref:#_when_a_plugin_is_refused[refusals]. One library reachable through several roots is loaded once. A symbolic link with a library name counts, so one whose target is missing fails the run with the path of the link. Anything that is not a library is ignored, so a directory can hold a README, an import library, or debug information without confusing the search. A file named `plugins` where the directory should be makes Mr.Docs warn that the directory could not be read, and the root contributes no plugins.

The libraries a plugin depends on go in the `plugins/lib` subdirectory. It has to be called `lib`: the name works on every platform, and it is the only one Mr.Docs adds to the Windows search path (on Linux and macOS the plugin's rpath names the directory, so any name works there). Mr.Docs never looks inside a subdirectory for plugins, so a dependency there is not mistaken for one:

[source]
----
my-addons/
└── plugins/
    ├── stats.dll        <1>
    └── lib/
        └── helper.dll   <2>
----
<1> The plugin.
<2> A library the plugin links to.

A plugin that can't be loaded, lacks `mrdocs_plugin_abi_version` or `mrdocs_plugin_init`, needs a newer Mr.Docs than the one running, or reports an error of its own stops the run. So does a generator whose id is taken, when the entry point returns the status that `mrdocs_register_generator` failed with, as the C++ wrapper and the example plugins do. The section on xref:#_when_a_plugin_is_refused[refusals] lists what Mr.Docs says in each case.

A library is opened with all of its symbols resolved at once, and keeps them to itself: a plugin that refers to something Mr.Docs or the system does not provide is refused while loading instead of crashing the first time it calls it, and two plugins cannot replace each other's functions. On Linux and macOS the message names the missing symbol, and adds that the plugin may need a newer Mr.Docs when the symbol is a function of the plugin API, which is what a plugin that uses something added after the ABI of the Mr.Docs that loads it looks like. On Windows the message only says that a module or procedure could not be found. On Windows, the libraries a plugin depends on are looked for in its own directory, then in the directory of the `mrdocs` executable, then in the `plugins/lib` directory of every addon root that has one (in no defined order among the roots), and then in the system directories, and not in the current directory or `PATH`. On Linux and macOS the plugin finds them through its own rpath, which `mrdocs::plugin` leaves empty, so the plugin sets it to the `lib` directory next to it; in CMake:

[source,cmake]
----
if (APPLE)
    set_target_properties(stats PROPERTIES INSTALL_RPATH "@loader_path/lib")
elseif (UNIX)
    set_target_properties(stats PROPERTIES INSTALL_RPATH "$ORIGIN/lib")
endif ()
set_target_properties(stats PROPERTIES BUILD_WITH_INSTALL_RPATH ON)
----

On macOS the rpath only applies to a dependency whose install name starts with `@rpath/`, which is what CMake gives its own `SHARED` targets; a prebuilt library with an absolute install name is looked up at that path and the copy in `plugins/lib` is ignored, so give it an `@rpath` name first (`install_name_tool -id @rpath/libfoo.dylib libfoo.dylib`). On Linux, a library in `plugins/lib` that depends on another one there needs an `$ORIGIN` rpath of its own, because a `RUNPATH` applies only to the library that carries it. On macOS the plugin's rpath also covers the `@rpath/` dependencies of its dependencies, so no further rpath is needed.

A dependency is also found through `LD_LIBRARY_PATH` (`DYLD_LIBRARY_PATH` on macOS) or in the system directories; the directory of the `mrdocs` executable is not searched. A loaded plugin stays loaded until the run ends.

A plugin is native code that runs inside the Mr.Docs process with the permissions of the user who runs it, and nothing sandboxes it or checks what it does: the interface is a way to write plugins, not a security boundary, so install only plugins you would be willing to run as a program, from authors you trust, the same way you would treat the `mrdocs` executable. The configuration decides which addon roots are searched, and every plugin in them is loaded whether or not its generator is selected, so running Mr.Docs on a configuration you do not trust (a cloned repository, a fork's pull request in CI) runs whatever plugins its addon directories hold, as it already runs the extension scripts there.

Once the library is there, the generator it installs is selectable like any other, through the xref:configuration/reference.adoc#generator_option[`generator`] option:

[source,yaml]
----
generator: stats
----

For the sample project that comes with the example, whose input describes a handful of symbols, the generator writes:

.`stats.txt`
[source,text]
----
include::example$examples/plugins/stats/sample-project/stats.txt[]
----

== A realistic example

The `stats` plugin is the smallest thing that uses every part of the interface. A plugin you write for a project usually reads more of the corpus than a symbol's kind. The {url-plugins}/deprecations[deprecations example] reports what the code marks as `\[[deprecated]]`, and uses the message of the attribute where the documentation has nothing to say. It has the same two parts, a generator and a transform, written on the wrapper.

Every symbol has an `attributes` array, with one object per attribute as written in the source (`Symbol::Attributes` in the C++ API). The `kind` of an attribute says which one it is, and a `\[[deprecated]]` carries its text in `message` (`DeprecatedAttribute::Message`), which is missing when the attribute has none. Both parts of the plugin need to find it, so the lookup is a function of its own, next to a test of which symbols to look at. The `extraction` of a symbol says how it got into the corpus. Only `regular` and `see-below` symbols are shown as their own; the others are a `dependency` (extracted only because a documented symbol uses it, such as a deprecated base class of another library) or `implementation-defined` (hidden by the configuration, such as a type in a `detail` namespace). A symbol can also be a copy of a base class member made for a derived class, which has `inheritedFrom` and is listed on the page of the derived class. The transform skips only the `dependency` and `implementation-defined` symbols, so the copy gets its brief too. The generator skips the copy as well, because it would be reported at the line of the derived class, and reports a base class member where it is declared:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/deprecations/plugin.cpp[tag=find]
----

Helpers read the parts of a symbol the report prints. The location comes from the `loc` object of the symbol, which holds a `loc` array of declarations and the `defLoc` of the definition when there is one. The report points at the first declaration, the one a user of the header sees and usually the one that carries the attribute (a later redeclaration may add `\[[deprecated]]`, and the report still names the first line), and falls back to the definition only for a symbol with no separate declaration. The scopes around a symbol are found by following its `parent` id with `Env::find`, up to the global namespace, which has no parent. A symbol or scope with no `name` field, such as an unnamed enumeration, is printed as `(anonymous)`, and the members of an anonymous namespace belong to the enclosing scope. An explicit or partial specialization has the same `name` as its primary template, so its `template.args` are printed after the name (`Box<int>`), with the scopes written in front of a type name (`Box<vendor::Old>`) and `...` for an argument that is more than a name or a constant:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/deprecations/plugin.cpp[tag=names]
----

The generator walks the symbols, and keeps what it needs from each deprecated one. An overload set is a symbol of its own that is deprecated when all its members are, so the generator skips it and reports the members. The handles a symbol gives out are released when the loop body returns, so the generator copies strings into the fields of its own `Entry`, sorts the entries by name, path and line, and only then writes the file:

.`plugin.cpp`
[source,cpp]
----
include::example$examples/plugins/deprecations/plugin.cpp[tag=build]
----

The transform finds the same attribute and writes the message into the documentation of a symbol that has no brief. It covers every symbol the documentation shows, including the copy of a deprecated base class member that a derived class page lists, while the generator reports the member only where it is declared. MrDocs makes the brief of an overload set from its members before the transforms run, so a set of deprecated functions with no documentation would show an empty description in the namespace listing. The transform gives such a set a brief of its own: the message the members share, or a plain "Deprecated." when they differ. It runs before the generator, so any output format shows the text, and the report is made from the same corpus:

.`plugin.cpp`

----

----

== When a plugin is refused

A plugin is there because the user put it there, so Mr.Docs doesn't silently skip a library that can't act as a plugin: one it can't load, one without the entry points, one for a newer interface, or one whose entry point fails. A plugin whose entry point succeeds and registers nothing is accepted without a diagnostic, so check the id of a generator that doesn't show up. For each of the messages in the first table, it stops the run before it extracts anything, exits with a failure status, and says which library and why. `<path>` below is the path of the library, and the text after the colon in the first message comes from the system loader.

[cols="2,3"]
|===
|Message |Cause

|`the plugin "<path>" could not be loaded: <system text>`
|The loader refused the library: a file that isn't a library, a missing dependency, or a symbol that nothing provides. On Linux and macOS, `; the plugin may need a newer MrDocs` follows when the missing symbol is a function of the plugin API.

|`plugin "<path>" needs a newer MrDocs (ABI 2, this MrDocs provides 1)`
|The plugin targets a later ABI version than this Mr.Docs provides.

|`plugin "<path>" reports ABI 0, which no MrDocs provides`
|`mrdocs_plugin_abi_version` returned zero.

|`the plugin "<path>" does not export mrdocs_plugin_abi_version`
|The library has no ABI function. A plugin written by hand without `extern "C"`, or built with hidden visibility and no export macro on that function, looks like this, and so does a dependency that was put in `plugins` instead of `plugins/lib`.

|`the plugin "<path>" does not export mrdocs_plugin_init`
|The library reports an ABI and has no entry point.

|`the plugin "<path>" failed: <message>`
|The entry point called `mrdocs_set_error`, whatever status it returned, or the plugin is a wrapper plugin whose entry point threw.

|`the plugin "<path>" failed with status <status>`
|The entry point returned a status other than ok (`plugin_error`, `invalid_arg`, `host_error`, and so on) and gave no message. When the last call to Mr.Docs failed, `; the last call to MrDocs failed: <reason>` follows.

|`the plugin "<path>" failed with status host_error; the last call to MrDocs failed: generator id="xml" already exists`
|The plugin registered a generator under an id that a built-in generator or an earlier plugin took. Plugins load in name order within a root, so the second one is refused.

|===

Two more messages are not refusals at load time. A callback that fails does so while the run is going, so it names a generator or a transform, and not a library, and the run stops with a failure status once that happens. A `plugins` entry that isn't a directory is only a warning, and the run goes on and exits as usual.

[cols="2,3"]
|===
|Message |Cause

|`the generator "<id>" failed: <message>` +
`the transform "<id>" failed: <message>`
|A callback reported an error after the corpus was built. The message is the plugin's. A callback that gave none is reported by its status, in the form of the entry point above for a generator (`the generator "<id>" failed with status <status>`), and as `the transform "<id>" failed: status <status>` for a transform. When a call to Mr.Docs failed earlier in the callback, either form ends with `; the last call to MrDocs failed: <reason>`.

|`The plugin directory "<directory>" could not be read: <system text>`
|A warning, not a failure: `plugins` exists but isn't a directory Mr.Docs can list.
|===

The info log level shows `Loaded plugin "<path>"` for each plugin that was loaded.

[#why-c]
== Why a C interface

A plugin runs inside the Mr.Docs process, so the question is what the two sides have to agree on. If the plugin used the {cpp} classes of Mr.Docs, as Clang plugins use the classes of Clang, it would have to be built with the same compiler, standard library, and flags as the `mrdocs` executable, and against the same revision of every header, since a {cpp} type has no stable layout. Mr.Docs changes often, and so does the LLVM it is built on, so every release would break the plugins that exist, and a plugin author would need to rebuild for each platform's compiler. Mr.Docs already has a stable description of its data: the DOM, the same values extension scripts read and write. A C interface over that description gives a compiled plugin what Lua and JavaScript extensions have, without a single {cpp} type crossing the boundary.

Two existing designs are copied on purpose, and the xref:contribute/binary-compatibility.adoc[binary compatibility] page, for contributors, lists each rule and where it comes from:

* The *loading model* is Clang's. A plugin is a shared library that is loaded into the tool and adds to the tool's registries. The entry point that receives an environment comes from Node-API's module initialization.
* The *ABI model* is Node-API's. Values are opaque handles, every function returns a status, one environment stands for one call, and a version number only grows, so that a plugin built once keeps loading into later releases. The header-only {cpp} wrapper is the counterpart of node-addon-api. Clang expects a plugin to be built against the same revision as the tool and leaves a mismatch to fail or crash, while Mr.Docs checks one ABI number instead and does not compare builds: the ABI version is the whole binary contract, and the only check the loader makes. The ABI number does not cover the DOM: a release may rename or remove a key, as it may for extension scripts, and a key that no longer exists reads as `undefined`, with a successful status, so a plugin that depends on a key checks the kind of the value it gets (`mrdocs_get_kind`, or `Value::kind()` in the wrapper) or asks first whether the key exists (`mrdocs_object_has`, or `Value::has()`), and reads the release notes. The keys are listed in the xref:generators/reference.adoc[generator reference].

== Versioning

The number is the _ABI version_ in `mrdocs/plugin.h`, `MRDOCS_PLUGIN_ABI_VERSION`. It changes when the header changes, and the header only grows: a new function or a new descriptor field is added under a new version, and no function is removed or changed. Every function in the header says which version it appeared in. A plugin reports the version it needs through `mrdocs_plugin_abi_version`, which is `MRDOCS_PLUGIN_ABI_TARGET`: the newest version by default, and a lower one if the plugin defines the macro before including the header, the way a Node-API addon defines `NAPI_VERSION`. Mr.Docs loads a plugin that needs its own version or an earlier one, and refuses a plugin that needs a later one with a message such as:

[source]
----
plugin "stats.so" needs a newer MrDocs (ABI 2, this MrDocs provides 1)
----

So a plugin keeps working with newer releases of Mr.Docs without a rebuild. It needs a newer Mr.Docs when its target is newer, whether or not it calls anything added in that version, and the target is the newest version in the header unless the plugin lowers it. A plugin meant for older releases defines `MRDOCS_PLUGIN_ABI_TARGET` as the newest version among the functions and descriptor fields it uses, which is the lowest ABI it needs. A change to the symbols a plugin reads that only adds, such as a new field, is a new key in the DOM and not a new version, because nothing about the interface changed. A plugin reads the keys it knows and ignores the rest.

Nothing about the compiler matters. A plugin and Mr.Docs share no {cpp} type, no standard library object, and no allocation, so the plugin can be built with any compiler, standard library, and runtime, and it doesn't have to match the ones Mr.Docs was built with. For the same reason, no exception may leave a callback (`build`, `apply`, `release`, the function given to `mrdocs_object_visit`, or the body of `MRDOCS_PLUGIN_INIT`): the runtime of the plugin may not be able to unwind through the frames of Mr.Docs, and the other way around. A {cpp} plugin catches what its code throws and turns it into a status, with `mrdocs_set_error` to explain the failure. The wrapper does this for every callback it registers, so the compiler and standard library of a wrapper plugin only have to agree with themselves. The calling convention doesn't depend on the compiler's options either. On Windows the default convention is a compiler option (`/Gv` and `/Gz` change it), so the header spells out `__cdecl` as `MRDOCS_PLUGIN_CALL` on every function, callback type and entry point, the way Node-API does with `NAPI_CDECL`, and a plugin built with those options still links, is found by its entry points, and is called the way Mr.Docs calls it. The convention is part of ABI 1 and never changes. A C plugin writes `MRDOCS_PLUGIN_CALL` on the callbacks it registers (`build`, `apply`, `release`, and the function given to `mrdocs_object_visit`), and the wrapper does it for its own.

[#platforms]
== Platform requirements

Nothing about the compiler matters, so the requirements are the ones of a shared library on the platform: a plugin for Windows is a DLL, a plugin for macOS is a module or dylib for the architecture of the `mrdocs` that loads it, and a plugin for Linux is an ELF shared object for it. The part that varies is the C library on Linux.

Plugins load into the `mrdocs` tool, which provides the `mrdocs_*` functions. On Windows a plugin imports them from a module named `mrdocs.exe`, so only the tool under that name loads plugins there: a renamed executable, or a program that embeds Mr.Docs and calls `loadPlugins`, cannot, and fails with the system's "module could not be found". On Linux and macOS a program that embeds Mr.Docs has to export the `mrdocs_*` functions from its executable, or the plugin is refused for a symbol that nothing provides, with the note that it may need a newer Mr.Docs.

The Linux release of Mr.Docs needs glibc 2.31 or later: Ubuntu 20.04, Debian 11, Fedora 32, RHEL 9, and anything newer. It links glibc dynamically, which is what lets it load a plugin, and it links the C++ runtime statically, so it depends on nothing from the system but glibc, which is compatible with later versions. The release follows the policy of the https://peps.python.org/pep-0600/[manylinux^] wheels: it is built on an old distribution with a current compiler, and a check on the finished binary fails the release if it needs a newer glibc, refers to a glibc tag that is not a version (such as `GLIBC_PRIVATE`), refers to the C++ runtime of the system, needs a library other than the ones of glibc, or is not dynamically linked against glibc. The xref:contribute/binary-compatibility.adoc#linux-release[binary compatibility] page has the reasons.

A plugin is not held to that floor by Mr.Docs, but by the machine it runs on. It links the C library of the machine that builds it, and can use whatever C++ runtime it likes, because no {cpp} object crosses the boundary. A plugin built on a newer distribution than the user's can need a newer glibc than the user has, and then fails to load with a message from the system loader about a glibc version. Build the plugin on the oldest distribution you want to support, as the release policy does, or ship it per distribution. Distributions that do not use glibc, such as Alpine, are not covered by the release.

One configuration can't load plugins: a Mr.Docs that you link with `-static`. A static glibc has no dependable way to load a shared library while it runs, and the startup files of a static link carry relocations that a shared object can't hold. The release is not linked that way, and a build of your own shouldn't be if you want plugins. The package config reports whether an installation can load plugins as `MRDOCS_BUILT_PLUGIN_MODULES`, which is off for such a build, so a project can ask before it tries. If you do link statically, configure with `MRDOCS_BUILD_PLUGIN_MODULES=OFF`, which only chooses whether a Mr.Docs build runs its own plugin tests and examples.
