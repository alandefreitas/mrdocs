= Workflow & PR hygiene

== Coding Standards

=== Paths

The AST visitor and metadata all use forward slashes to represent file pathnames, even on Windows.
This is so the generated reference documentation does not vary based on the platform.

=== Exceptions

Errors thrown by the program should always have type `Exception`.
Objects of this type are capable of transporting an `Error` object.
This is important for the scripting to work; exceptions are used to propagate errors from library code to scripts and back to the invoking code.
For exceptional cases, these thrown exceptions should be uncaught.
The tool installs an uncaught exception handler that prints a stack trace and exits the process immediately.

=== The plugin interface

A xref:extensions/plugins.adoc[plugin] is compiled against `include/mrdocs/plugin.h`, a C header, and loaded into the running tool. Nothing {cpp} crosses that boundary, so the public {cpp} headers and the metadata types can change without breaking a plugin. What a plugin reads is the DOM, though, so the DOM keys and the configuration options are part of what plugins (and extension scripts) depend on: adding a field or an option is free, since a new field is a new key, while renaming or removing one, or changing the string a `kind` maps to, breaks the plugins that read it without the ABI version telling them. Treat those changes with the same care as a change that breaks extension scripts.

The rule that governs the header is _additive only_. It has a version, `MRDOCS_PLUGIN_ABI_VERSION`, and it only grows. Adding a function or a descriptor field raises it in the same commit, and the new declaration says in its comment which version it appeared in. Never remove or change a function, a constant, or the layout of a structure that is already there: a plugin built against an earlier version keeps calling it. Descriptor structures begin with their own size, and new fields go at the end, declared under `#if MRDOCS_PLUGIN_ABI_TARGET >= n` like a function, so that a plugin which targets an older version cannot set a field that an older Mr.Docs would ignore. The {cpp} wrapper in `include/mrdocs/plugin.hpp` is part of the same surface: a new function gets its wrapper member in the same commit, declared under the same `#if MRDOCS_PLUGIN_ABI_TARGET >= n` as the function it calls, so that a plugin which targets an older ABI still compiles. The core paths of the wrapper only use functions of ABI 1. The wrapper uses nothing but `plugin.h`, so it never mentions a type of Mr.Docs. The xref:contribute/binary-compatibility.adoc[binary compatibility] page explains where the rule comes from and why it is not negotiable.

Every function, type, and constant in `plugin.h` carries its version in its doc comment, as a `@since ABI n` line (the macros that only select linkage and visibility are not part of the ABI and do not, but the calling convention macro `MRDOCS_PLUGIN_CALL` is, and says ABI 1), and the comment of a structure field added later says the same. Read the line as a promise: a plugin that targets ABI n can call the function on every Mr.Docs that provides ABI n or later, and the loader refuses a plugin built for a later ABI than the running Mr.Docs provides. How it is refused depends on what the plugin uses. A plugin that uses nothing added after the running version gets the message `plugin "<path>" needs a newer MrDocs (ABI n, this MrDocs provides m)`. A plugin that calls a function added after the running version (the header only declares it for a target of at least n, so such a plugin was built with a newer header than the running Mr.Docs) is refused earlier, while the system loader resolves its symbols: the message carries the loader's text, followed on Linux and macOS by `the plugin may need a newer MrDocs`. A test of the refusal for a new function has to expect that second form.

To add a function to the interface:

. Declare it in `include/mrdocs/plugin.h`, with the `MRDOCS_PLUGIN_API` marker followed by the return type and `MRDOCS_PLUGIN_CALL` (the calling convention, which a callback type or a callback field of a descriptor names too, as in `(MRDOCS_PLUGIN_CALL *build)`), a `mrdocs_` prefix, and a doc comment that ends in `@since ABI n`: the prefix is what the export lists of the `mrdocs` executable match, and the export test fails if the executable exports a `mrdocs_` function the header does not declare or lacks one it does (that test runs on Linux and macOS builds with narrowed exports; step 5 covers Windows). Like every function of the header, it takes the environment first and returns a `mrdocs_status`, and leaves its output parameters alone when it fails. For an `n` above 1, put the declaration inside `#if MRDOCS_PLUGIN_ABI_TARGET >= n`, so that a plugin which targets an older version cannot call it by mistake.
. Raise `MRDOCS_PLUGIN_ABI_VERSION` by one, which makes it `n`. This holds even if the previous version has not been released yet: the numbers are cheap, and a version that gains functions after a plugin was built against it would break the promise of the `@since` line.
. Implement it in `src/mrdocs/Plugin/CApi.cpp` as a thin wrapper over the DOM, and catch every exception at the boundary: none may reach the plugin.
. Add the wrapper member to `include/mrdocs/plugin.hpp` under the same `#if`, and a row to the table of the xref:extensions/plugins.adoc#wrapper[wrapper section] of the Plugins page.
. Name the function in `tests/plugin-api/LinkProbe.cpp`, which links against the tool's exports and is the check that the Windows build exports it.
. Add a unit test in `tests/unit/Plugin/CApi.cpp` for the function and for its failure cases, and use it from a plugin in `tests/plugin-api` when the function is part of a path the plugins exercise.
. Document it on the Plugins page when it changes what a plugin author can do.

To add a field to a descriptor (`mrdocs_generator_desc` or `mrdocs_transform_desc`):

. Raise `MRDOCS_PLUGIN_ABI_VERSION` by one, declare the field at the end of the structure under `#if MRDOCS_PLUGIN_ABI_TARGET >= n`, and say in its comment that it appeared in ABI `n` and what an unset (zero) field means, because that is what every plugin built for an earlier version leaves it as.
. Read it in `src/mrdocs/Plugin/CApi.cpp` only from the copy the register function makes with `copyDescriptor`, never from the plugin's pointer: the plugin's structure ends where its own `struct_size` says, and the bytes after it are not the plugin's. The registration functions check `struct_size` against the size of the fields of ABI 1 and nothing more, so a field of ABI `n` may be missing from the descriptor of a plugin that targets an earlier version.
. Add a test that registers a descriptor of the older size with poison bytes after it, or a descriptor whose `struct_size` stops before the new field, and checks that the field reads as unset (`testDescriptorCopy` in `tests/unit/Plugin/CApi.cpp` is the model).
. Record the offset and the type of the field, and the new size of the structure, in `tests/plugin-api/abi/AbiBaseline.c` as for a function.

Changing what an existing function does is not an addition even when its signature stays: that includes the order it visits values in, the statuses it returns, and the meaning of a field. If a behavior has to change, add a new function with the new behavior under a new version and leave the old one as it is.

== Style Guide

This project follows informal formatting conventions established by previous Boost projects.
To help contributors, we provide a `.clang-format` file that encodes these rules.

* Do *not* apply clang-format across entire files or the whole project.
* Use the config only as a *reference* for your IDE/editor, or to format the code you **personally add or modify** in a commit.
* Always check the surrounding code and keep consistent with it.
* Do not create style-only commits that introduce large diffs without functional changes.

Why This Approach:

* Keeps history clean: avoids large, style-only commits.
* Ensures new contributors are not lost when adapting to project style.
* Encourages consistency without rigid automation.

General Advice: When in doubt, copy the style of the surrounding code.
The `.clang-format` file is a tool to help you, not a rule to enforce blindly.

The utility script `./utils/reformat.sh` can also be used to check a few project invariants, such as header guards and include order.
