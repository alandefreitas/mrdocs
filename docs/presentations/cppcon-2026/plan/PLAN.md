# The plan: how every claim in the research becomes a property of the deck

[research/HOW-TO-GIVE-GREAT-TALKS.md](../research/HOW-TO-GIVE-GREAT-TALKS.md) has 175 claims about what makes a talk work. This directory turns them into properties that are either **enforced** (a schema will not accept a file without them), **checked** (a script fails when they are missing), **reviewed** (a read-through that is recorded and required), or **logged** (a preparation act that is counted). Nothing in the deck exists that did not come from a file in this directory, and every file is validated against the one above it, so the final HTML is a product of the plan and not a thing edited by hand.

The pattern is a hierarchical data file whose schema guarantees the presence of everything the final document must contain, a checker that proves the rendered document reflects the data, and a build that produces the deliverable from the data. Here there are more levels, because a talk is written top-down: what it is for, then the argument, then the timed beats, then the slides, then the HTML, and, alongside, what the speaker did to prepare.

## The levels

Each level is a YAML file in `levels/`, validated against a JSON Schema, written as YAML, in `schemas/` (JSON Schema, written as YAML so descriptions can run to several lines), then checked against the levels above it by `tools/pipeline.py`. A level may not be written until the one above it validates.

## Facts, decisions and constraints in the meta file

The meta file mixes three kinds of field, and each field's comment says which it is and where the value came from. A **fact** is a value about the world (the date, the slot, that the talk is recorded); the tool cannot verify it, it can only carry it, so the comment names the source and the date it was checked. A **decision** is a choice we made (the idea statement, ten minutes for questions and not announcing it); other levels are checked against it, which is what makes writing it down worth anything. A **constraint** is a value the schema fixes (`aspect: "16:9"`); its job is to be enforced downstream, by the HTML checks or by later schemas, not to be an input. Anything that is a preparation fact rather than a fact about the talk (the room, the equipment) lives in `logs/logs.yml`, where it may be null until known and a check warns until it is filled in.

## Time

The research offers only rules of thumb about time, all of them expert opinion: about a minute per slide (Naegle, Alley, the most common figure among the advice articles), more than one visual per minute is too many (Bourne), show less on more slides (Conway, whose deck had 277 slides in ninety minutes). These agree only for slides that carry text; for a word slide or a picture the time on screen is the time the sentence about it takes to say, which no rule of thumb gives. So time in this pipeline comes from the script, not from a rule, and is tracked at three levels that must agree:

- **beats** carry `target_minutes` that sum to the talk (P18); the meta file's talk time is the budget, beats with a target take theirs from it, and the beats without one share what is left in proportion to the minutes their notes take to say; a beat with a target and no notes yet is estimated at its target;
- **slides** carry a `duration_s`, derived from the notes at the speaking rate unless declared to override it (a live demo, a pause), that sums to the talk within ten percent (S4);
- the **notes** imply a speaking time at the speaking rate in the meta file (120 until a rehearsal is recorded: the research names no best rate and its only direction on pace is slower, so the estimate is made to err long, and a slide it flags as over-full really is), and S27 fails a slide whose declared duration is less than 0.6 of that or more than 1.6 times it, and fails the deck when the notes add up to more than fifteen percent off the talk.

`pipeline.py pace` prints, per beat, the target, the declared slide time and the estimated speaking time, so a beat can be rehearsed on its own against a five-minute target instead of the whole hour. The generated deck also carries `data-timing` on every slide, so reveal's speaker view (press S) shows a pacing bar per slide during a run-through, green when on time.

## The four kinds of enforcement

The research says some things a schema can require, some a script can measure, some only a reader can judge, and some are things the speaker does rather than things the deck has. Each claim is assigned exactly one or more of these, and `levels/0-criteria.yml` records which.

- **schema**: the field must exist and have the shape. "Three take-home points, a problem, a proof and an action" is an object with those three required keys and no others. "A decorative image" cannot be expressed because `image_role` has only `represents` and `explains`. "A bullet list" cannot be expressed because no slide kind renders one.
- **script**: a script measures it. Word counts, durations, orders, cross-references between levels, file existence, string containment (the promise in the opening notes, the transition words in the beat's first slide, the one idea on the last slide), CSS values, contrast ratios.
- **review**: a human or an AI reads the artefact and records a verdict in `logs/logs.yml`. Five reviews are defined: narrative flow (R1), humour placement (R2), familiarity of metaphors (R3), each slide's point surviving a lapsed listener (R4), and delivery on the recording (R5). The pipeline can require them (`--strict`) but cannot perform them; what it can do is make sure the artefact they judge already has every structural property, so the reviewer judges prose and not structure.
- **logged**: the speaker did something and wrote it down; the script counts entries. Rehearsals, equipment tests, the room visit.

Thirty-one claims are **informational** and map to `N/A` with a note: mechanisms, background, and all seventeen entries of the research's Myths section. A myth is a belief the research found unsupported, and refuting a belief creates no criterion: that "animation makes it clearer" is unproven does not make "less animation" worth enforcing, and the research's actual finding on animation is that the wins came from motion carrying information, which is what a magic move does. Where a myth contradicts a positive finding, that finding is already mapped under its own claim and the myth's note says which one.

A few checks carry a number the research does not: the six-minute pacing threshold (P22), the twenty-slide floor (S4), the 40 px type floor (H4), the single zoom transition (H9). Their descriptions in `levels/0-criteria.yml` say "policy" and name the expert source they lean on, so nobody mistakes a design choice for evidence.

## Vocabulary

- **Act**: a division of the story (Conway, Duarte): a run of the talk that sits on the story spine, on one side of the gap between what is and what could be, aims at a feeling, and asserts **claims** backed by evidence. Four acts: the story (what is, and the turn to what could be), the tour, the surprise (extensions, the star moment), the new normal. The audience never hears the word.
- **Chapter**: a section of the tour as shown to the audience on the roadmap, with a mnemonic image. The chapters are the nav parents of the docs. Only the tour has chapters; the story and the close have none.
- **Beat**: one stretch of speech with one point to make. It belongs to an act, has target minutes, **transition words** (what is said to open it, so a listener who drifted can rejoin), and lists the act's claims it carries, or states its purpose when it carries none (an opening, a demo, an ask). A tour beat also names its chapter and lists the docs pages it covers.
- **Slide**: what is on screen while a beat is spoken, listed under the beat; every beat has one or more, so order and contiguity are given by the file. A slide of kind `same` keeps the previous picture and changes only the notes, which is what a speaker does instead of a blank. A slide of kind `rendered` shows the documentation Mr.Docs generated from the code on the slide before it, so an example is always the input and then the real output, never an output described in a comment. A code frame names its file in a tab (`title`), and a step may hold two frames (`blocks`), so two files are never one block. A code slide, step or block may name a `file` in the repository (with an `include` of tags or lines, as the docs do) instead of carrying a copy of the code; the build reads it, so the plan holds pointers to examples that already exist as files. On a single-block code slide each highlight is a point: it is written as `lines` plus the `notes` said while it is lit, the speaker view changes notes with the fragment, and S12 fails a highlight with nothing to say. The tour's example slides are transcribed from the docs pages by `tools/docs_examples.py`: every source block on a page becomes a code slide and every rendered preview a `rendered` slide, built here with the release binary from the same fixture the docs build uses. Those slides are glances: a few words of notes, on screen for the seconds the words take, and the timing model treats them so (S4, S27). A slide has one assertion, exact on-screen text, notes written as speech, a duration, and how it moves from the previous slide.
- **Claim**: something an act asserts, with evidence, carried by at least one beat of the act (P28). Claims are the argument; the pages the tour visits are the beats' docs lists, not the claims.

## The transitions, and what is proven at each

The point of the levels is that each transition is a conversion an AI or a person performs, and the file it produces can be checked against the file it came from before anyone reads it for taste.

1. **Research to criteria.** Mechanical. Every bullet in the research becomes a criterion with an id derived from its section; the map in `criteria_map.py` attaches checks. The tool reports any bullet left unmapped and any check id that does not exist, so the registry cannot silently fall behind the research.
2. **Meta to plan.** A person (or an AI given the meta file) writes the argument as acts, and the beats under each act put minutes on it. The checks prove the story frames the meta file's what-is / what-could-be as a gap and alternates across it, and that every claim has evidence. The story also carries the brain dump, so "did you consider what you could say before choosing" is a count, not a promise.
   The beat checks then prove The checks prove the minutes add up to the meta file's talk time, every beat belongs to an act that exists, systems are explained after their parts, and nothing runs six minutes without a breath.
   Within the plan, the AI drafts slides under each beat; this is where the conversion from explicit claims to narrative notes happens, and it is the step that cannot be proven by a script. What *can* be proven: every beat has slides, the beat's transition words open its first slide's notes, the on-screen text is within the limits for its kind and does not repeat the notes, every picture is explained in speech, every slide carries its assertion, and the closing slide shows the one idea word for word. The reviews (R1, R4) then judge the prose that the checks have already shaped.
3. **Slides to HTML.** Mechanical. The generator renders each kind into the theme's markup; the HTML checks then prove the rendering did not lose anything (sections, ids, order, notes) and did not add anything the research forbids (bullets, backgrounds, logos, autoplay, italic runs).
4. **Deck to delivery.** Nothing converts here; the speaker rehearses and records what happened, and the counts gate the final `--strict` run.

## The report

`pipeline.py report` runs everything and then prints, per research claim, whether its checks passed, failed, are pending, or are not applicable. A claim shows `ok` only when every check mapped to it passed. This is the list to work down: a `FAIL` next to `C3-3-05` means the one-minute-per-slide ceiling is currently broken, and the message from `S4` says by which slide.

`--strict` turns warnings into failures and requires the review sign-offs and the rehearsal counts, so it is the mode to run the week of the talk; without it the pipeline reports structure only and lets content be drafted incrementally.

## Decisions the pipeline forced

Constraints in the research that changed the deck the moment they became checks:

- **Five chapters, not six.** The docs nav has six top-level sections. The research caps a talk at five chapters (P10, P11), so Contribute is folded into the closing call to action rather than being a chapter.
- **No separate "thank you" slide.** The last slide must be the conclusions and must stay up through questions (S1, S16). The old deck's thank-you slide was removed and its notes moved into the conclusions.
- **Call to action before the conclusions**, so the last thing on screen is the idea (S1).
- **No corner mascot on content slides.** Winston and Conway both say remove logos; the generator does not emit the persistent badge (H6). The mascot lives on the covers.
- **Slide numbers off, arrows only on hover** (`policies.slide_numbers_visible: false`): Conway warns that numbers read as a countdown, and the arrows are clutter on the recording. The speaker's aids live in a separate build, `pipeline.py build --rehearsal` (faint numbers, visible arrows, `build/rehearsal.html`), so the deliverable can never carry them by accident; M12 warns if the policy is flipped.
- **Word-count limits rather than "less text".** The research found that cutting text alone does not help; what helps is a claim over a picture and words in speech. So the limits are per kind (three words on a word slide, fourteen on a line, none on a picture) and the check that matters is S9, that on-screen text is not a transcript of the notes.

## Working with it

```bash
plan/check.sh                                     # rebuild both decks and validate, in one go (flags pass through: plan/check.sh --strict)
python3 plan/tools/pipeline.py build --rehearsal # practice deck with faint slide numbers and visible arrows (build/rehearsal.html)
python3 plan/tools/pipeline.py criteria          # regenerate levels/0-criteria.yml after editing the research or the map
python3 plan/tools/pipeline.py validate          # schemas and checks, structure only
python3 plan/tools/pipeline.py build             # plan/build/index.html
python3 plan/tools/pipeline.py build --artifacts # also deck.pdf and contact-sheet.png (needs Chrome and ImageMagick)
python3 plan/tools/pipeline.py report            # validate, then criteria coverage
python3 plan/tools/rendered_examples.py          # regenerate assets/rendered/*.html from the example code on the slides (needs the release binary)
python3 plan/tools/docs_examples.py              # rebuild assets/rendered/docs/*.html from the docs' own examples (build/docs-slides.yml is the slide list they were spliced from)
python3 plan/tools/feature_highlights.py        # light the lines that use the feature on every example slide before a rendered slide (skips slides that have highlights)
cd docs/ui && npx browserify ../presentations/cppcon-2026/vendor/mrdocs-highlight.entry.js -o ../presentations/cppcon-2026/vendor/mrdocs-highlight.js   # rebundle the docs' highlighter (doc-comment colouring) after changing docs/ui/src/js/vendor/mrdocs-highlight-languages.js
python3 plan/tools/pipeline.py report --strict   # the week of the talk: reviews and rehearsals required
python3 plan/tools/pipeline.py build --out index.html   # when the generated deck replaces the hand-made one
```

The order of work is top down: edit `1-meta.yml` until M passes, then `2-plan.yml` until P and S pass (acts and claims first, then beats, then slides), then `build/index.htl`, then build and fix H, then rehearse and log. A failing check at a lower level is never fixed by editing the level below it.

## What this does not do

It cannot judge whether a sentence is good, whether a metaphor lands, or whether the speaker was compelling; those are the five reviews, and they are required, not automated. It cannot know whether a fact is true; facts only Alan can confirm are flagged `verify: true` in the story and the pipeline refuses `--strict` until each is marked `verified`. And it cannot make the talk interesting. What it can do is guarantee that when a reviewer finally reads the deck, every structural property the research asks for is already there, so the reviewer's whole attention goes to the things only a reader can see.
